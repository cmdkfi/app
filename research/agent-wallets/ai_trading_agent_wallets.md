# AI Trading-Agent Wallets ("give your agent a wallet and tell it what to trade"), 2025–2026

Research date: 2026-10-20; Bloom Trading drain added 2026-10-26; Binance hot-wallet theft added 2026-10-30. Scope: how hosted and self-hosted AI trading-agent wallet products work technically, where the agent runs, who holds the key, what limits exist, and what has gone wrong. All claims carry inline sources; items I could not source are listed under Gaps. Custody language is treated skeptically throughout: "non-custodial" in marketing usually means "the vendor's key-infrastructure provider (Privy/Turnkey/Coinbase) holds key shares in an enclave and the vendor's server holds a signer credential", not "the key is only on the user's device".

## Key Question 0: How do these products work technically? (taxonomy of execution location and key holder)

### Takeaway
Across the category there are only four real architectures: (A) vendor-hosted agent + vendor-controlled signer credential on a Privy/Turnkey/CDP enclave wallet (Bankr, Wayfinder, Nansen, Virtuals, Coinbase Agentic Wallets); (B) vendor-hosted agent + a raw key generated and stored in the vendor's database (Telegram bots, most "AI trading bot" Telegram products, the aixbt simulation wallet); (C) agent running on the user's own machine with a key on disk (ElizaOS self-hosted, OpenClaw skills, MCP wallet servers, Olas Pearl); (D) agent running in a TEE with a key that is generated inside the enclave and never exists in plaintext outside it (Phala/dstack, Oasis ROFL/WT3, NEAR Shade Agents, Marlin Oyster). Only (C) keeps the key "only on the user's device", and (C) is also where keys sit in plaintext `.env` files and get harvested by infostealers.

### Cited Findings
- A January 2026 systematic review (317 works screened from 3,000+) proposes a five-pattern taxonomy of agent/blockchain integration: read-only analytics, simulation and intent generation, delegated execution, autonomous signing, and multi-agent workflows; it compares 20+ systems across 13 dimensions including custody model, permissioning, policy enforcement, observability and recovery, and lists prompt injection, policy misuse, key compromise, adversarial execution dynamics and multi-agent collusion as the threat model. It contains no experiments; it proposes a "Transaction Intent Schema" and "Policy Decision Record" as future work. — [arXiv:2601.04583, Alqithami, submitted 8 Jan 2026](https://arxiv.org/abs/2601.04583)
- Privy's signer model: an app can "add signers to wallets so they can act within defined permissions" for "offline actions, such as limit orders or agentic trades while a user is away"; a signer "will never see the wallet's private key"; signing happens "in a secure enclave that only your application can make authorized requests to". — [Privy docs: signers overview](https://docs.privy.io/wallets/using-wallets/session-signers/overview)
- Privy distinguishes "agent-owned wallets" (the agent provisions and controls the wallet and holds the credential that triggers signing, no user prompt) from "delegated signing" (agent transacts from a user's existing wallet under an authorization key scoped by policies; user can revoke at any time). Policies can restrict tokens and chains, cap transfer value per transaction or per time window, and allowlist recipient addresses and contracts. The Privy Agent CLI uses a browser device-authorization flow; later transactions use short-lived ephemeral signing keys, sessions last up to 30 days with token rotation. — [Privy docs: agent wallets](https://docs.privy.io/wallets/overview/solutions/agent-wallets)
- Privy key export: for Solana embedded wallets the private key is shown in an iframe on a separate domain so "the app cannot access it"; programmatic (server-side) export "may affect the app's custody", must be enabled by Privy Support, and is supported only for TEE-based wallets, not on-device wallets. — [Privy docs: export](https://docs.privy.io/wallets/wallets/export); [Privy docs: programmatic export](https://docs.privy.io/wallets/wallets/programmatic-export)
- Turnkey: private key generation runs in "Secure Enclaves", "a type of Trusted Execution Environment"; QuorumOS provides remote attestation; policy evaluation runs inside the enclaves; "no single engineer can access any enclave or reconstruct a secret". The page does not state that Turnkey-the-company cannot access keys, and names no audits. — [Turnkey docs: security approach](https://docs.turnkey.com/security/our-approach)
- Coinbase CDP Wallets: signing happens inside a Trusted Execution Environment so keys "stay out of reach even of Coinbase" (beta-era launch page); policies are project- or account-scoped and can check destination address and value, with USD spend limits per transaction. — [Coinbase CDP Wallets launch](https://www.coinbase.com/developer-platform/discover/launches/cdp-wallets-launch); [CDP policies docs](https://docs.cdp.coinbase.com/wallet-api/v2/using-the-wallet-api/policies)
- Coinbase's head of engineering for CDP, Erik Reppel, on the baseline the category is replacing: "most agents with wallets just have a private key sitting on disk somewhere"; the TEE design is "several orders of magnitude safer than just having a private key on disk" though "no sandbox protocol is perfect". — [Decrypt, 12 Feb 2026](https://decrypt.co/357813/coinbase-launches-wallet-ai-agents-built-in-guardrails)
- Telegram trading bots (non-AI but the custody baseline for "bot wallets"): "the bot operator generates and stores the private key on their servers... if bot servers are compromised, every user's funds are at risk"; Halborn's COO in 2023: "These bots lack a proper security audit, provide no insights into the storage methods for private keys"; CertiK: "extremely high-risk and unsuitable for medium to long-term storage of assets". — [The Block, 2023](https://www.theblock.co/post/241386/telegram-crypto-bots); [Cointelegraph](https://cointelegraph.com/news/should-telegram-trading-bots-be-trusted)
- SlowMist's recurring finding in audits: attackers "planted malicious prompts in MCP responses" that "poisoned the agent's context and led it to call a wallet plugin for an on-chain transfer"; "the flaw lies in corrupted task orchestration rather than in the model writing bad code". — [TechFlow summary of SlowMist/Bitget report, Mar 2026](https://techflowpost.com/en-US/article/30729)

### Inferences
- "Where the LLM runs" and "where the key is" are separable. In every hosted product below, the LLM call goes to a third-party model API (Anthropic/OpenAI/xAI) regardless of whether signing is in an enclave; the model provider sees the prompts. Only Secret Network/Phala GPU-TEE setups claim to keep inference confidential.
- The security-relevant question is not "custodial vs non-custodial" but "what credential can trigger the enclave to sign, who holds it, and what policy is evaluated inside the enclave before signing". If the vendor's server holds an authorization key with no policy (the Bankr Grok wallet), a prompt injection is equivalent to key theft.

### Gaps
- No a16z crypto or Paradigm essay specifically on agent wallet custody surfaced; the only a16z custody writing found was its April 2025 SEC letter on RIA custody, unrelated to AI agents. — [Decrypt](https://decrypt.co/315213/a16z-sec-update-crypto-custody-rules-registered-investment-advisers)

## Key Question 1: Hosted chat-to-trade agents (Bankr, aixbt, Hey Anon, Griffain, Wayfinder, Virtuals, Coinbase, Nansen, Almanak, Giza, Orbit, etc.)

### Takeaway
Hosted products run the LLM loop and the execution loop on vendor servers and sign via a Privy/Turnkey/Alchemy/Coinbase enclave wallet to which the vendor's backend holds the signer credential; the user gets policy knobs (Bankr has the most detailed public set: daily/per-tx USD caps, recipient allowlists with cooldown, price-impact guard, arbitrary-call toggle) but in no hosted product does the user's device hold the only key.

### Inferences
- Bankr is the clearest example of "non-custodial" marketing meeting server-side reality: wallets are Privy embedded wallets that are non-exportable, the Bankr backend signs on behalf of the X/Telegram/web identity, and the May 2026 Grok drain shows a prompt is sufficient to move funds when the policy layer is permissive. Bankr's post-incident security page is now the most detailed user-facing policy set in the category.
- Wayfinder/Turnkey "session-based pre-approval" is a delegated-signing design: the user authorizes a time-boxed session, after which Parallel's backend can request signatures from Turnkey without further user prompts. "Non-custodial" here means Parallel does not hold the raw key; it does hold a credential good for the session window.
- Nansen is the only major hosted product found that requires per-transaction user approval, which puts it in the review's "simulation and intent generation" pattern rather than "autonomous signing".

## Key Question 2: Incidents 2025–2026

### Takeaway
Every confirmed loss in the category traces to one of three causes: (1) prompt/instruction injection into an agent that holds a signer credential with no human gate (Bankr/Grok, May 2026, ~$150K–$180K; Lobstar Wilde, Feb 2026, ~$442K, arguably a misread request rather than an attack); (2) compromise of the operator's control plane or user devices rather than the enclave (aixbt dashboard, Mar 2025, ~$100K; Bankr 14 wallets, May 2026, est. $150K–$440K, root cause unpublished); (3) supply-chain malware in agent skill marketplaces harvesting on-disk keys (386 malicious ClawHub skills, Feb 2026). The Bloom Trading drain of 26 Oct 2026 (~9,408 SOL, ~$954K, ~49 wallets) is a custodial Telegram bot, not an LLM agent; its cause is unconfirmed as of the same day and it fits (2) or a key leak. No Privy, Turnkey or Coinbase enclave compromise was found. The Binance hot-wallet theft of 29 Oct 2026 (about $6.3B, Binance's estimate) is an exchange, not an agent, and is (2) at the largest scale so far: by Binance's preliminary account, a compromised engineer's laptop reached a service container that submitted withdrawals, with no key leaked.

### Inferences
- The Grok wallet drain is a pure authorization-design failure, not a cryptographic one: Bankr's server held a signer credential for a wallet whose only "owner" was an X account, and tool permissions were gated by NFT ownership that the attacker could satisfy by airdropping the NFT. Any product in which a social-media identity is the wallet owner inherits this.
- Bankr telling 14-wallet victims that a "seed phrase" was compromised is inconsistent with its own docs ("no seed phrase to share"), suggesting those victims' external/imported wallets or device-level compromise, or that Bankr has wallet types not described in the security page. Treat the root cause as unknown until a post-mortem appears.
- ClawHub/OpenClaw incidents show the self-hosted model's failure mode is not the agent runtime but the skill supply chain plus plaintext credentials on disk.
- Custodial Telegram bots drain in waves because one operator holds every key: BONKbot 2024 (~$523K, 302 victims), Nova 2025, Bloom 2026 (~$954K, ~49 wallets). Once a key has leaked, revoking permissions does nothing; only moving funds to fresh keys helps. The relevant contrast for PRIME is not AI versus no AI but who holds the key and what can be signed with it.

### Gaps
- No Bankr post-mortem for the 14-wallet breach was found as of Oct 2026; confirmed total loss and whether reimbursements completed are unverified.
- No incident involving a Privy, Turnkey or Coinbase enclave compromise was found; Halborn's "custodial wallet layer" remark is speculation.
- No confirmed drain of a specific Virtuals GAME agent wallet was found; Crypto Briefing's "$150,000" figure matches the Bankr/Grok incident rather than a Virtuals one.
- No rekt.news write-up on any of these incidents surfaced in search; rekt coverage may exist but was not retrieved.
- Amounts for the Grok drain vary across outlets ($150K/$155K/$170K/$180K) because DRB price moved; recovery percentage (80% vs 88%) is also contested.

## Key Question 3: Local / self-hosted options — does the key really stay only on the user's device?

### Takeaway
Yes for ElizaOS self-hosted, OpenClaw skills, most MCP wallet servers, CCXT MCP and Olas Pearl: the key is generated and used on the user's machine. But in ElizaOS/OpenClaw/MCP it is typically a plaintext `EVM_PRIVATE_KEY`/`keypair.json` with no policy engine, the LLM prompts still go to a cloud model provider, and the dominant real-world loss vector is infostealers and malicious skills reading those files. Pearl is the only local product found that wraps the key in Safe smart accounts with backup/recovery, but its on-disk key-storage format is not documented publicly.

### Cited Findings
- **ElizaOS** `@elizaos/plugin-evm`: the one required variable is `EVM_PRIVATE_KEY=your-private-key-here` set in `.env`; the plugin loads when `process.env.EVM_PRIVATE_KEY?.trim()` is non-empty. — [plugin-evm README](https://unpkg.com/@elizaos/plugin-evm@1.0.13/README.md); [ElizaOS docs](https://docs.elizaos.ai/plugins/defi/evm/examples); QuickNode's guide instructs users to paste the key into `.env`. — [QuickNode](https://www.quicknode.com/guides/ai/how-to-setup-an-ai-agent-with-eliza-ai16z-framework)
- ElizaOS TEE mode: `TEE_MODE` (OFF/LOCAL/DOCKER/PRODUCTION), `TEE_VENDOR=phala`, `WALLET_SECRET_SALT` (8–128 chars) as the key-derivation input; `elizaos tee phala` wraps Phala Cloud CLI. — [ElizaOS TEE integration guide](https://docs.elizaos.ai/guides/tee-integration); Phala's dstack SDK derives keys from the app root key inside the container and returns the same key for the same unique ID, with a viem helper. — [Phala docs: create crypto wallet](https://docs.phala.network/phala-cloud/phala-cloud-user-guides/building-with-tee/create-crypto-wallet)
- **OpenClaw**: `~/.openclaw/device.json` holds a device private key (stolen by infostealers); skills such as polyclawster store a Polygon private key in a local config file and sign locally. — [BleepingComputer](https://www.bleepingcomputer.com/news/security/infostealer-malware-found-stealing-openclaw-secrets-for-first-time/); [Open Skill Index](https://openskillindex.com/skills/openclaw-skills-polyclawster-agent)
- **MCP wallet servers**: CCXT's official MCP server runs locally, "the model never sees the keys", trading is off unless enabled. — [CCXT docs](https://docs.ccxt.com/docs/mcp); Agent Wallet MCP (Solana) stores the keypair at `~/.agent-wallet/keypair.json`, devnet only, "private key never leaves your machine". — [Glama listing](https://glama.ai/mcp/servers/@noah-ing/agent-wallet-mcp); Stacks MCP keeps keys in an encrypted local file with 15-minute auto-lock. — [Glama listing](https://glama.ai/mcp/servers/@kai-builder/stacksagent-mcp/blob/af7b8661dbec47e413edd40a1e190b7cfc7eb4a4/README.md)
- **Coinbase Agentic Wallet MCP** is the exception among MCP tools: keys are in Coinbase TEEs, and the MCP server can only pay x402 services, not send or trade. — [CDP docs](https://docs.cdp.coinbase.com/agentic-wallet/welcome)
- **Olas Pearl**: desktop app for Windows/macOS/Linux; "agents run on your own device rather than centralized servers"; "fully self-custodial, including Safe wallets"; a "Pearl recovery phrase" can be imported into an external wallet; backup via Google/Apple account or a user-controlled backup wallet that can recover funds via Safe; agents listed: Connect (wallet for Claude Code/Codex with Polymarket, Robinhood Chain, Olas Marketplace), Polystrat (Polymarket), Omenstrat, Basius (DeFi), Optimus (unavailable), Agents.fun (unavailable); chains Polygon, Gnosis, Base, Optimism, Robinhood Chain; agents earn OLAS rewards and are evicted after missing two consecutive ~24h activity cycles; funding by card. Minimum 800 MB RAM, 1.3 GB disk. — [pearl.you](https://www.pearl.you/)
- Pearl Connect (beta, Gnosis + Polygon): "creates a Safe smart account for the user and runs locally within Pearl"; "each transaction is signed locally on the user's machine, with private keys kept outside the AI session"; positioned as a user-directed co-pilot, not autonomous trader (syndicated single story). — [IT Brief](https://itbrief.co.uk/story/olas-launches-pearl-connect-for-claude-coding-agents)
- Pearl source: Electron + Next.js frontend with a Python backend under `operate/`; Apache-2.0. — [valory-xyz/olas-operate-app](https://github.com/valory-xyz/olas-operate-app)
- Phala's own page on local-key risk: an agent on Phala can "generate, store, and use private keys inside an enclave" so "keys never exist in plaintext outside the TEE, even to the developer". — [Phala](https://phala.com/solutions/ai-agents)
- Helius guidance: "private keys stored in code create massive vulnerabilities"; an agent with direct wallet access can make irreversible unintended transactions. — [Helius](https://www.helius.dev/blog/how-to-build-a-secure-ai-agent-on-solana)

### Inferences
- A local agent satisfies "key only on my device" but not "secure": with ElizaOS/OpenClaw the key is readable by any process the user runs, there is no spend policy between the LLM's tool call and the signer, and the prompt (including balances and strategy) leaves the device to the model API unless a local model is used.
- Pearl's Safe-based design (agent EOA as Safe signer, user-controlled backup owner) is structurally better than a raw EOA because a compromised agent key can be rotated out of the Safe by the backup owner, but I could not verify the on-disk encryption of the agent EOA key.

### Gaps
- Pearl's key-storage mechanism (password-encrypted keystore vs plaintext, Master EOA/Safe vs agent EOA/Safe hierarchy): not found in pearl.you, SECURITY.md, or the repo landing page; would require reading `operate/` source.
- Brave/Phantom local agents: nothing retrieved.
- "IronClaw" appears only as a listed Phala example ("Ironclaw (NEAR security)"); no documentation on a local IronClaw trading setup was found.

## Key Question 4: TEE-hosted agents (Phala, Oasis ROFL/WT3, NEAR Shade Agents, Marlin Oyster, Secret Network)

### Takeaway
TEE products guarantee that the signing key is generated inside an attested enclave bound to a specific code hash, so neither the developer nor the cloud operator can extract it and the running code can be verified on-chain; they do not guarantee the LLM is correct, that external tool/LLM-API calls are inside the trust boundary, or that spend policy exists unless the developer writes it into the contract. NEAR deprecated the standalone Shade Agent framework in April 2026 and its docs state it was never formally audited; Secret Network moved to a semi-permissioned model after 2025 TEE exploits.

### Cited Findings
- **NEAR Shade Agents**: each agent runs off-chain in a TEE paired with a NEAR "agent contract" that stores the approved code hash and checks attestation before letting the agent act; signing uses NEAR Chain Signatures (MPC) for Ethereum, Solana, Bitcoin etc.; docs recommend contract-enforced guardrails (allowed functions, chains, spend caps, e.g. 0.1 ETH per 24h) "to protect funds even if a worker's key is extracted"; deployment guide warns the technology "has not yet undergone a formal audit". — [NEAR docs: deploying](https://docs.near.org/ai/shade-agents/deploying); [NEAR docs: production components](https://docs.near.org/ai/shade-agents/production/production-components); [Aurora blog](https://aurora.dev/blog/shade-agents-and-aurora-virtual-chains-the-future-of-autonomous-ai-on-near)
- NEAR docs notice: "The Shade Agent Framework will no longer be maintained as standalone developer tooling after April 19, 2026"; remains open source; docs moved to the GitHub monorepo. — [docs.near.org/ai/shade-agents/key-components](https://docs.near.org/ai/shade-agents/key-components); [NearDeFi/shade-agent-framework docs](https://github.com/NearDeFi/shade-agent-framework/tree/main/docs)
- Live example: the "Mindshare Index AI Agent" (Q2 2025), described as "the world's first autonomous trading bot that executes trades based on social sentiment signals captured by Kaito AI... fully onchain with verifiable logic and no manual intervention"; docs describe it swapping SOL for NEAR when Solana mindshare rises. — [Nansen NEAR Q2 2025 report](https://research.nansen.ai/articles/near-quarterly-report-q2-2025); Phala Cloud offers a NEAR Shade Agent template (testnet prerequisites). — [Phala template](https://cloud.phala.com/templates/near-shade-agent)
- **Oasis ROFL / WT3**: announced late April 2026; "operates within a trusted execution environment (TEE), ensuring its inner logic and strategies remain confidential while its integrity is publicly verifiable"; runs on ROFL + Sapphire; trades on Hyperliquid and others; strategy signals from Ocean Predictoor; seeded with $100,000 from the Oasis Protocol Foundation; a share of returns funds ROSE buybacks (50% per one secondary source). — [Oasis blog](https://oasis.net/blog/wt3-trustless-defi-trading-agent); [Oasis agents page](https://oasis.net/ai-agents); [zkAGI on Oasis](https://oasis.net/blog/zkagi-trustless-trading-agents)
- **Phala (dstack/TDX)**: the TDX quote covers the compose-hash "including the system prompt, model digest, and tool list"; each tool call is signed with a per-app key chained to the TDX root; verification via dcap-qvl against Intel's root and `DstackKms.sol`/`DstackApp.sol` on-chain; "No host process ever sees plaintext"; tool list and credential scope bounded by compose-hash, "no runtime path can widen privilege"; revoking a compose-hash kills access; example wallet "caps spending at $50/day with 2/2 multi-sig". Caveat on the page itself: external tools (Gmail, Stripe) "are outside the trust boundary"; it does not say whether third-party LLM calls (Claude Sonnet 4.5, Gemini 2.5 Pro in catalog) run inside the enclave. Listed agents: Eliza, Clawdi (OpenClaw), Hermes (Nous), Agent Wallet (x402/ERC-8004), Claude Code, Codex, Ironclaw (NEAR security). — [Phala solutions page](https://phala.com/solutions/ai-agents)
- **Marlin Oyster**: Solana agent server where `/init` creates the wallet "using the TEE-derived key"; address stays stable across redeployments of the same code; ERC-8004 attestation verification. — [Marlin research forum](https://research.marlin.org/t/building-persistent-ai-agents-on-solana-with-marlin-tees/105); [Marlin ERC-8004](https://research.marlin.org/t/building-trustless-ai-agent-infrastructure-with-erc-8004-and-marlins-oyster-tees/130)
- **Secret Network**: SecretAI uses NVIDIA GPU TEEs for confidential inference; Jan 2026 roadmap says SecretAI/SecretVM are "ready for prime time" and notes a move to a "semi-permissioned network model" after the wiretap.fail, tee.fail and Battering Ram TEE exploits; ElizaOS integration into the Secret AI SDK announced Feb 2025. No agent-wallet product found. — [Secret Network 2026 roadmap, 12 Jan 2026](https://scrt.network/blog/secret-network-2026-roadmap); [Secret AI docs](https://docs.scrt.network/secret-network-documentation/secret-ai); [Eliza Labs partnership](https://scrt.network/blog/secret-network-and-eliza-labs-join-forces)
- **Almanak** also states it uses TEEs for strategy privacy on top of Safe/Zodiac custody. — [iq.wiki](https://iq.wiki/wiki/almanak)

### Inferences
- TEE agents convert "trust the operator" into "trust Intel TDX / AMD SEV plus the code hash plus whoever can upgrade it". Secret Network's own acknowledgement of wiretap.fail/tee.fail/Battering Ram shows the hardware root of trust has had practical breaks in 2025.
- Shade Agents' contract-side spend caps are the right pattern (policy enforced by the chain, not the agent), but with the framework unmaintained since April 2026 and unaudited, a trading product built on it would be self-supported.

### Gaps
- No public performance or audit data for WT3 beyond Oasis's own announcements.
- Whether Phala/dstack-hosted agents keep LLM inference inside the enclave (vs calling Anthropic/Google APIs) is not stated on the solutions page.
- No evidence found of whether the Mindshare Index agent is still running on mainnet in 2026.
